# CRM review — 7 September 2026

The CRM has substantial feature coverage, but the next investment should be security, reliable automation, and consistent financial data. The findings below include an authentication boundary failure, incorrect folio accounting, stalled workflows, and lost mobile writes. These should take precedence over adding more modules.

This is a repository-wide review of the working tree at commit `fd98bbe`, including existing uncommitted changes. It inventories 71 dashboard sections, 301 web page files, 500 API route files, 238 migration files, and 58 mobile route files. Critical execution paths were traced in depth; remaining modules were sampled or inventoried. This is **not a claim that every screen, database operation, or live integration passed an end-to-end test**. The workspace changed during the review; findings refer to the source inspected and checks described below.

No application source was changed by this audit. No production data, orders, messages, credentials, or deployments were modified. The only audit deliverables added are this report and the dependency scan JSON.

**Security findings.**

**S1 — Critical: an unsigned request header is accepted as a session.** [Session parsing](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/auth/session.ts:86>) returns JSON from `x-mfd-session` without signature verification. [Middleware public-route returns](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/middleware.ts:191>) preserve that caller-supplied header. Omitting `iat` and `sid` also skips the corresponding revocation checks. On public-prefix endpoints that call `requireSession`, an anonymous caller can impersonate a known user. In particular, [2FA setup](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/auth/2fa/setup/route.ts:28>) replaces the user's secret and sets `two_fa_enabled=false`; private local-file access also depends on this session reader. This is source-confirmed; no account was modified.

Verify a signed cookie/Bearer credential in the Node session reader. Strip internal identity headers on every incoming request, including public routes. Require recent authentication for factor replacement and keep the existing factor active until its replacement is confirmed. Acceptance: a fabricated identity header without a valid credential must be rejected on every session-dependent endpoint.

**S2 — High: public document submission accepts storage objects it does not own.** [Document submission](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/public/docs/submit/route.ts:170>) reads a submitted `storageKey` with shared storage credentials. Invalid/oversized objects may be deleted; accepted objects are attached to the submitter's tenant. The key is not bound to the collection token, subject and tenant. A valid share link plus a known foreign key is sufficient for the source path. Persist upload grants and accept only their exact keys; never delete an unowned object during validation. Test two tenants and two collection links, including invalid-file cleanup.

**S3 — High: RM/branch restrictions are missing from some read APIs.** [Full client details](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/investors/[id]/full/route.ts:36>) checks a broad view capability but loads by investor ID without the shared [record-scope condition](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/investors/access.ts:74>). With restricted data scope enabled, another RM in the tenant can retrieve a known client's complete record. [Global search](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/search/route.ts:19>) also checks only the session and searches all six record groups without per-module or RM scope checks. Tenant RLS does not enforce ownership within a firm. Centralize authorized record loaders and apply them to search, details, documents, exports, statements and valuations. Test owner, marketing, two RMs, and two branches.

**S4 — High: device logout can be defeated by refreshing the old token.** [Refresh](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/auth/refresh/route.ts:32>) checks global revocation, but not device-session revocation, before minting a new session. [Device logout](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/me/devices/[id]/route.ts:28>) revokes the old session row only. Validate the old device/session family before refresh, preserve the revocation chain, and check current account status. Acceptance: a token revoked via the device list must fail both normal API access and refresh.

**S5 — High: the login limiter does not prevent continued password evaluation.** [Web login](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/auth/login/route.ts:66>) and [mobile login](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/auth/mobile-login/route.ts:64>) compare the password before consulting the limiter, which is only consulted on failure. Guesses continue being evaluated after the failure budget is exhausted, and a correct guess still succeeds. Check an existing lock before password comparison, record failures separately, and use shared counters with trusted proxy/IP handling. Test that an exhausted failure budget prevents another password check until it expires.

**S6 — High, configuration-dependent: WhatsApp webhooks accept unsigned events when the secret is missing.** [Vartify webhook verification](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/webhooks/vartify/route.ts:41>) allows this in production as well as development. Forged events can affect inbound records, delivery status, consent and downstream automation. Fail closed when the secret is absent and expose the integration as unverified. Add replay/freshness checks where the provider's signature format supports them. Actual production secret configuration was not inspected.

**S7 — High: workflow HTTP actions can access the worker's private network.** [The HTTP handler](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/workflow/actions/http_request.ts:27>) fetches a configurable URL with configurable method/headers and stores the response. [The schema](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/workflow/schema.ts:94>) validates URL syntax only. A user able to publish and execute a workflow can target network destinations reachable from the worker. Restrict protocols/destinations, resolve and check address ranges, recheck redirects, and enforce egress controls. Allow private integrations only through explicitly approved destinations. Infrastructure-level controls were not verified.

**Automation and communication findings.**

**A1 — High: delays and event waits can stall indefinitely.** [Pause persistence](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/workflow/runner.ts:270>) leaves the current node at the waiting node. [Delay execution](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/workflow/actions/delay.ts:7>) computes a new future deadline every time it runs. A wake therefore pauses again. [Event resumption](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/workers/outbox-poller.ts:243>) requeues without selecting `matched`; timeout awakening does not select `timeout` either. An isolated actual-handler probe confirmed a zero-minute delay returns `pause` on both executions. Persist a resume outcome/target and advance exactly once. Test delay, matched event, timeout, duplicate event and worker restart.

**A2 — High: WhatsApp template sends bypass blocking compliance findings.** [The pipeline condition](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/comms/pipeline.ts:424>) only blocks when `compliance.blocked && !isWhatsappTemplate`. Thus a template send proceeds despite a blocking content finding. [Consent handling](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/comms/pipeline.ts:267>) separately permits missing consent and blocks explicit revocations only; its comment describes this as a firm preference. This conflicts with the supplied developer guide's explicit-consent, non-bypassable-gate contract. Apply a consistent policy to all send paths and validate rendered template variables. Document and resolve the consent-policy discrepancy with the product owner; this audit is not a legal compliance certification.

**A3 — High: campaign concurrency and failure handling can duplicate or indefinitely retry recipients.** [Planning locks](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/workers/campaign-dispatcher.ts:62>) end before valid recipients are durably reserved. Another dispatcher can select them before sending finishes. [Dispatch](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/workers/campaign-dispatcher.ts:192>) supplies no stable recipient idempotency key. A provider failure is recorded and then thrown inside a transaction, rolling back that failure record; the next pass can select the recipient again. Persist uniquely keyed campaign-recipient delivery records, claim them atomically, retain attempt history independently, and use bounded retries/backoff. Test two workers plus crashes before/after provider acknowledgement; never assume a timeout means a message was not sent.

**A4 — High: the SIP rejection recipe cannot evaluate its declared reason fields.** [Recipe predicates](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/recipes/sip_rejection_followup.ts:19>) refer to `event.reason_code`, but [predicate lookup](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/filter/predicate.ts:57>) requires the field in the investor catalog. Actual branch execution with `insufficient_balance` raised unknown-field errors and selected `default`. Event payloads are also nested differently from some recipe expression paths. Define a typed event context, normalize paths, and validate all installed recipe predicates and tokens before publication. Test each rejection reason through the actual runner.

**A5 — Medium: valid long workflows are abandoned after 26 immediate steps.** [The worker's step budget](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/workers/workflow-runner.ts:90>) stops execution but leaves the run `running`. Future claims exclude it; the stalled-run reaper can then fail it. Requeue a run that exhausts its execution budget and distinguish active leases from abandoned work. Test a graph longer than 26 immediate steps and multi-iteration loops.

**A6 — Medium: recurring schedule occurrences can be duplicated or lost.** [Schedule scanning](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/workers/master-scheduler.ts:14>) does not atomically claim occurrences; the [watermark update](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/workers/master-scheduler.ts:52>) is unconditional and occurs before the run is safely created. Two workers can dispatch the same subjectless occurrence; a crash can skip one. Create a uniquely keyed `(trigger, scheduled occurrence)` job in the same transaction as watermark advancement.

**A7 — Medium: claimed scheduled jobs lack crash recovery.** [Scheduled communications](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/workers/scheduled-comms.ts:29>) become `queued` before processing, while subsequent scans select `scheduled`. [Scheduled workflow rules](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/workers/workflow-rules-scheduler.ts:29>) similarly strand `running` jobs. Add expiring claims, recovery/reconciliation, attempt limits, and stable delivery keys. Validate process termination immediately after a claim.

**A8 — Medium: a missing branch edge falls back to another branch.** [Edge selection](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/workflow/runner.ts:315>) falls back to the first outgoing edge when the requested handle is absent. [Validation](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/workflow/schema.ts:389>) warns that the missing path will end instead. Reject incomplete branching at publication or explicitly stop/fail on an unmatched handle. Test a nonmatching investor against a graph without a default edge.

Automatic task creation is [intentionally disabled](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/workflow/actions/create_task.ts:4>) per a recorded firm preference. Preserve that decision, but show the disabled action clearly in recipe previews and readiness rather than advertising task creation that will not occur.

**Data correctness and mobile findings.**

**D1 — High: valuation omits another folio holding the same scheme.** [Snapshot exclusion](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/finance/valuation.ts:297>) uses scheme coverage from transaction history without respecting folio identity. An isolated call to the actual valuation function used F1 with 10 units at ₹12 from transactions and F2 with 20 units at ₹12 from a snapshot. Expected ₹360; actual ₹120. Reconcile by investor, AMC, folio and scheme, with explicit snapshot dates/history coverage. Use one valuation contract across persisted AUM, profile, portal and PDF. Test partial-history imports and multiple folios of one scheme.

**D2 — High: FIFO consumes acquisition lots from the wrong folio.** [The gains query](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/tax/realized-gains.ts:73>) omits folio identity, and [lot queues](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/tax/realized-gains.ts:97>) are keyed by scheme only; the open-lot function repeats this. Actual-function reproduction: F1 buys 5 units at ₹10 in January 2024, F2 buys 5 at ₹20 in April 2026, and F2 sells 5 at ₹30 in September 2026. Expected F2 cost ₹100/gain ₹50; actual cost ₹50/gain ₹100 using F1's older lot. Preserve folio identity throughout gains and harvesting, and report unmatched redemption units. This concerns software record identity; current tax-law treatment was not reviewed.

**D3 — High: invalid mobile startup sessions can leave prior-account data available for restoration/replay.** [Session hydration](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/mobile/src/state/session.ts:34>) can move `loading → guest`, while [cleanup](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/mobile/app/_layout.tsx:86>) runs only for `authed → guest`. The [query cache](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/mobile/src/api/queryPersist.ts:30>) and [offline queue](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/mobile/src/lib/offlineQueue.ts:21>) use global keys. The next authenticated shell restores and flushes using its current token. Bind persisted records to tenant/user and verify ownership before restore/replay; clear or quarantine state on invalid startup sessions. Ordinary explicit logout already has cleanup. This path was traced in code, not tested on a device.

**D4 — High: mobile offline changes can be silently lost.** [Retry handling](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/mobile/src/lib/offlineQueue.ts:85>) retains network/timeouts but drops HTTP 503/429. [Flush completion](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/mobile/src/lib/offlineQueue.ts:95>) replaces the live queue with an old snapshot, losing concurrently enqueued work. The queue also discards oldest entries after 100. Two isolated executions of the actual transpiled module reproduced loss after a 503 and loss of a write added during a flush. Acknowledge successful IDs individually, preserve new entries, retain transient failures, and expose permanent failures/full capacity to the user. Add server idempotency before retrying ambiguous POST outcomes.

**D5 — Medium: historical statements use a current NAV for a historical valuation label.** [Statement pricing](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/finance/account-statement.ts:98>) joins the latest NAV, then prices closing units while the [page label](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/dashboard/investors/[id]/statement/page.tsx:180>) says the value is as of the requested end date. Use dated NAV history on/before the period end. Until supported, state the actual pricing date separately from the transaction period.

**D6 — Medium: return summaries conflate unknown cost with zero return and omit closed-position performance.** [Snapshot-only holdings](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/finance/valuation.ts:325>) use market value as invested cost. An unknown-cost ₹240 snapshot therefore returns invested ₹240 and return 0. [Cashflow filtering](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/finance/valuation.ts:336>) excludes fully redeemed positions: buy ₹100/sell ₹120 produced portfolio gain 0/XIRR null despite a realised gain of ₹20. Represent unknown cost as null; distinguish current holdings from lifetime account performance and show cost/history coverage.

**D7 — Medium: catching an import row's SQL error does not recover the transaction.** [RTA inserts](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/rta/process.ts:344>) share a transaction; [error handling](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/rta/process.ts:369>) catches failures without a savepoint. Subsequent statements can then fail because the transaction is aborted. [Ingestion failure handling](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/rta/ingest.ts:78>) also attempts to update status in that same transaction. Validate/stage first; either isolate rows/batches with savepoints or deliberately roll back an atomic import and record its failure in a fresh transaction. PostgreSQL documents recovery through [ROLLBACK TO SAVEPOINT](https://www.postgresql.org/docs/16/sql-rollback-to.html). No malformed file was imported into a live database.

**D8 — Medium: undoing a client merge does not restore all relationships.** [Merge](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/lib/investors/merge.ts:142>) repoints special relationships such as lead referral/conversion, family primary investor and activity subject without journaling their original values in `moved`. [Unmerge](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/investors/unmerge/route.ts:75>) restores recorded investor references only. Journal every changed reference/field and define conflict handling for changes made after the merge. Test a merge→unmerge round trip across every supported relationship.

**D9 — Medium: referral follow-up task insertion disagrees with the task schema.** [Lead conversion](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/app/api/leads/[id]/convert/route.ts:299>) inserts `kind` and `created_by`, while the [schema](<C:/Users/PRITESH THAKOR/Downloads/MYCRM/src/db/schema/tasks.ts:44>) defines `type`, `created_by_id`, and required `subject_type`. The failure is logged rather than surfaced. Use typed insertion and include the subject; reconcile this path with the firm's automatic-task policy. Validate a referred lead conversion against a disposable migrated database.
